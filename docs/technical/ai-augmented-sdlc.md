# AI-Augmented SDLC — the full cycle

This document describes, phase by phase, how AI participates in the software lifecycle in this project, and where human decision is mandatory. Final responsibility for correctness, security, and quality always rests with the developer — the structure below exists to make that verifiable, not merely asserted.

## 1. Planning: from PRD to traceable milestone

The planning layer is the **PayFlow SDLC Kit** (`.claude/agents/wiz-*.md`, `.claude/commands/wiz-*.md`), an adapted fork of [wiz-cursor](https://github.com/NSXBet/wiz-cursor) — see `.claude/NOTICE.md` for what was ported and what was extended in this repository.

1. The PRD (`docs/product/PRD.md`) and technical specification (`docs/technical/`) are written with AI support for structure, but scope and priority decisions are human — AI points out gaps, it does not decide.
2. `/wiz-prd <slug> "<ideia>"` generates the planning PRD via Q&A. Clarifying questions are generated by AI and **answered by a human** — that is how hallucination is contained at this stage: the plan does not advance without explicit decisions on points that require judgment (test policy, NFR priority, scope trade-offs).
3. `/wiz-phases <slug>` decomposes the PRD into **phases**, and `/wiz-milestones <slug>` decomposes each phase into **milestones** identified in the format `P0XM0Y` (phase X, milestone Y). Planning state lives in `.wiz/<slug>/` — `prd.md`, `phases/phaseN.md`, and later `reviews/` and `retros/`. Mapping that plan to a board (epic / task / subtask) existed via skill + Jira API and is described in `.claude/jira-visibility.md`; it is not executed in this repository.
4. A milestone is only implementable when it has **testable acceptance criteria** (Definition of Ready, see `docs/technical/quality/qa-guidelines.md`). The context that governs implementation is not embedded in the milestone: `.wiz/context/authoritative-sources.md` points to the guidelines in `docs/technical/guidelines/` that must be loaded from source on each run — that is what makes it possible to implement without inventing requirements or depending on AI to "remember" the convention.

Every line of code is traceable to a human-approved requirement — not to a loose conversation with AI.

## 2. Architecture and ADRs

- Trade-offs (monolith vs. microservices, outbox vs. direct broker publication, centralized gateway vs. distributed authentication) are discussed with AI as a *sparring partner*: the proposal comes from payment systems experience, AI helps map consequences and edge cases.
- Every relevant architectural decision becomes an ADR (`docs/decisions/`), with alternatives considered and consequences — not just the final decision.

## 3. Implementation

`/wiz-next [slug]` executes the next `🚧 TODO` milestone:

1. Reads the milestone acceptance criteria and loads local context (phase + guidelines pointed to by `.wiz/context/authoritative-sources.md`).
2. Consults the language specialist (`wiz-typescript-specialist` for Backoffice, `wiz-go-specialist` for CORE, among others) when applying the guideline leaves doubt.
3. Implements.
4. Runs local gates — lint, build, tests (`docs/technical/ci-cd.md`, `scripts/pre-commit.sh`).
5. The language specialist reviews the diff, **mandatory before commit** — a code pattern check, not a full NFR audit. Failure requires correction and a new review before proceeding.
6. Commit in Conventional Commits, with milestone status updated to `✅ COMPLETE`.

That specialist review is local to each milestone. Formal audit against P0–P4 gates is done on demand, separately: `/wiz-review-milestone <slug> <id>` for a specific milestone, `/wiz-review-phase <slug> <n>` for the entire phase — both delegate to the `wiz-reviewer` agent and the note goes to `.wiz/<slug>/reviews/`.

Outside the milestone flow — bug fix, point investigation, documentation adjustment — work is conducted via structured prompt directly, without going through `wiz-*` commands. See `docs/technical/prompt-engineering.md`.

## 4. Testing

Unit and e2e tests are derived from acceptance criteria and edge cases specified in the milestone (idempotency, invalid state transition, malformed payload) — not generated from code already written, which would produce tests that merely confirm existing behavior without validating the business rule.

## 5. Review and quality

- Each milestone corresponds to one or a few small, descriptive commits, reviewable in isolation.
- CI gates (`docs/technical/ci-cd.md`) are the same regardless of whether code was written with or without AI.
- Formal review produces an artifact: when `/wiz-review-milestone` or `/wiz-review-phase` runs, the note goes to `.wiz/<slug>/reviews/`, following `PULL_REQUEST_TEMPLATE.md` — what was checked against applicable guidelines, findings (including non-blocking ones, recorded as conscious technical debt instead of omitted) and verdict.
- A review finding does not end at commit: when closing a phase, `/wiz-retro` (`wiz-retro-analyst` agent) groups phase review findings by deviation type and decides, per group, whether it becomes a guideline update, ADR, or remains accepted debt (`docs/technical/retrospective.md`). The report goes to `.wiz/<slug>/retros/`.
- Process metrics defined in `docs/technical/quality/ai-process-metrics.md`.

## 6. Limits and responsibility

- Security decisions (`docs/technical/architecture/security.md`) are specified and validated by a human; AI implements following the specification, not the other way around.
- SDLC Kit agents **defer** to `docs/technical/guidelines/` — none carries its own convention. An agent with an opinion diverging from the documented guideline would create a second source of truth, and that is what the single-source rule avoids.
- No data, credentials, or business logic from real systems is used as input for AI in this project.
